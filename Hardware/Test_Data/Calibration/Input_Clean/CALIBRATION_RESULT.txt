Thrust axis (commanded thrust N vs achieved vertical accel, down_m_s2)
-------------------------------------------------------------------
Scored by analyze_input_calibration.py's "thrust" pseudo-axis (cmd[:,3]/B_T
vs Acceleration.down_m_s2, same cross-corr r/lag/gain machinery as wx/wy/wz).
19/47 runs reliable (r>=0.5) -- notably better-conditioned than the rate axes;
accelerometer response to thrust is cleaner to measure than body rate tracking.

  r = 0.771 (n=18)   lag = 36.8 ms (n=14)   gain = 0.745 m/s^2 per N (n=15)

Sanity check: gain ~= 1/mass (F=ma). Naive (no drag) model, R2-weighted over the 19
reliable runs: gain=0.7830, implied mass=1.277kg vs known 1.204kg (+6.1%).

RESOLVED 2026-07-21: root-caused as aerodynamic drag missing from the naive point-mass
model. Adding a Velocity Body.z_m_s term (a = gain*B_T + k*v_z + c) and refitting:
  gain=0.8217, implied mass=1.217kg (+1.1% -- closes the gap almost entirely)
A quadratic drag term (k*v_z*|v_z|) was also tested and is WORSE (gain=0.8022, +3.5%),
so linear drag is the right functional form, not a refinement target. Ground effect
(altitude term) and battery-voltage/thermal effects were also tested and ruled out
(altitude coefficient sign-flips inconsistently across runs -- overfitting, not signal;
restricting to the confirmed-valid 22.4-24.0V battery plateau made no difference once
the reliability filter was applied correctly). See project_hardware_drone_mass memory
for the full investigation, including a self-corrected methodology bug along the way
(an early pass accidentally dropped the r>=0.5 filter, producing a misleadingly large
+15-19% gap that did not survive re-checking).

FINALIZED CALIBRATION FACTORS -- for use in the next landing test
=======================================================
Consolidated 2026-07-21, REVISED to r^2-weighted method (see below). These
are CORRECTION factors: since gain = achieved/commanded, dividing a commanded
value by its axis's gain (equivalently multiplying by 1/gain) before sending
it should make the ACHIEVED response match the ORIGINALLY INTENDED value.
Not yet wired into any script -- this is the reference to apply.

Methodology change from the first version of this table: the r>=0.5-then-
MAD-trim method has a hard boundary discontinuity (r=0.49 fully excluded,
r=0.51 fully included), which is unstable exactly where it matters most --
confirmed on wy, whose aggregate r sat right at the 0.5 cutoff. Switched to
an r^2-weighted mean across ALL 47 runs (every run contributes, weighted by
variance explained, no arbitrary threshold) -- see
Hardware/scripts/analyze_input_calibration.py::r2_weighted_mean(). This
changed wx and wz meaningfully too, not just wy -- run the script directly
to reproduce/update rather than trusting a stale hand-copy of these numbers.

2026-07-22 -- Genuine sensor/vibration noise floor: FILTERED, calibration re-run
=======================================================
Root cause of the noisy a_down plots (see §3 in the notebook): PSD of a
representative run's a_down showed a clean bimodal split -- ~51% of power
below 2Hz (real maneuver/thrust-response signal), a quiet gap 2-20Hz (~5%),
then ~44% of power above 20Hz (propeller/motor vibration). Cross-checked
against the PURE-THRUST hover sine-sweep data (zero commanded body rate, so
any rotation-coupling confound is absent by construction): the two pure-
thrust runs showed 30.5% and 13.9% power in the 20-92Hz band respectively --
disagreeing with EACH OTHER by more than either disagrees from the
combined-rate input-cal run's 43.7%. Conclusion: genuine vibration is
present and flight-to-flight variable regardless of whether body rates are
commanded; rotation-coupling (gravity-projection change from a rotating
body-frame accelerometer) is a real but NOT dominant contributor -- broadband
vibration is the primary noise source, consistent everywhere checked.

Filter applied: 4th-order zero-phase (filtfilt) Butterworth low-pass,
cutoff=8Hz, sitting in the middle of the empirically-identified quiet gap.
Applied to ALL telemetry signals used in ANY input-cal parameter (gyro for
wx/wy/wz, accelerometer for thrust, velocity for the drag-correction term)
in analyze_input_calibration.py::per_run_metrics -- i.e. for every
parameter, not just thrust. Implemented as a shared _lowpass() helper;
filtfilt (zero-phase) specifically chosen so the filter doesn't introduce
lag that would bias the cross-correlation lag/gain estimates downstream.

Effect on reliability counts (r>=0.5, per-axis): wx 7->8, wy 6->8, wz
15->17, thrust stayed 19 but its aggregate r improved 0.771->0.867.
Filtering measurably helped across every parameter, not just thrust.

FINAL VALUES (filtered, drag-corrected where applicable, R2-weighted) --
supersede the 2026-07-21 unfiltered numbers above:
  wx correction: gain=1.550 -> 1/gain = 0.645  (was 0.664 unfiltered)
  wy correction: gain=1.389 -> 1/gain = 0.720  (was 0.699 unfiltered)
  wz correction: gain=1.451 -> 1/gain = 0.689  (was 0.696 unfiltered)
  HW_THRUST_SLOPE_N_PER_UNIT = 31.59  (drag-corrected + filtered gain=0.8546,

2026-07-22 -- Adaptive per-run trim: rescuing drift-truncated runs
=======================================================
Motivation: many runs (esp. 2026-07-21's STEP_HOLD_S=3.0s batch) get
soft-cutoff-truncated by GRADUAL altitude-drift buildup, not a sudden
corruption event -- the EARLY portion of a long hold, before drift
accumulates, is still clean command-tracking data. Scoring a whole run as
one blob lets a drift-corrupted tail drag down an otherwise-good early
segment and get the whole run discarded. Confirmed directly: trimming 5 of
17 tested 2026-07-21 runs to their first 2s alone flipped them from
unreliable (avg r<0.5) to reliable (avg r 0.61-0.89).

Implemented properly as `best_trim_metrics()` in
analyze_input_calibration.py: for each run, tries t_max in
[full, 3.0, 2.5, 2.0, 1.5, 1.0]s and keeps whichever gives the best mean
wx/wy/wz r (rate axes) or best thrust r (thrust axis, scored separately
since its best window can differ from the rate axes'). `per_run_metrics()`
gained an optional `t_max` parameter to support this.

RESULT -- reliable-run counts roughly DOUBLED or better across every
parameter (17 runs rescued for rate axes, 15 more for thrust):
  wx: 7  -> 23 reliable / 47   (n_eff 6.61 -> 13.88)
  wy: 6  -> 24 reliable / 47   (n_eff 5.96 -> 15.59)
  wz: 15 -> 28 reliable / 47   (n_eff 10.51 -> 17.56)
  thrust: 19 -> 34 reliable / 47

FINAL VALUES (adaptive-trim, filtered, drag-corrected where applicable,
R2-weighted) -- supersede the whole-run-only 2026-07-22 numbers above:
  wx correction: gain=1.319 -> 1/gain = 0.758  (was 0.645, full-run-only)
  wy correction: gain=1.354 -> 1/gain = 0.739  (was 0.720, full-run-only)
  wz correction: gain=1.504 -> 1/gain = 0.665  (was 0.689, full-run-only)
  HW_THRUST_SLOPE_N_PER_UNIT = 31.98  (drag-corrected gain=0.8409, implied
    mass=1.189kg, -1.2% off known 1.204kg -- TIGHTER than the full-run-only
    -2.8% gap; was 31.59 full-run-only)
  HW_HOVER_THROTTLE_NORM = 0.42  (rounded from 0.4226 R2-weighted
    intercept-derived value; was 0.41/0.4095 full-run-only)

M_correction = diag(0.758, 0.739, 0.665)
