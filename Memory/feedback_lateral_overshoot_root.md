**The lateral wall, root-caused (2026-06-14, GT-verified via tools/gt_optical_flow.py).** At IC2 (2,2,5) the drone fails NOT on approach but at close range:
1. **Approach WORKS** — the outer PID drives `s_e_n` down; GT lateral offset closes 2.6m -> ~0.8m by alt ~2m. `s_e_n` and `ds_d` are genuine and sensible. The PID is NOT the failing element and its input is fine.
2. **Then it OVERSHOOTS** — at ~0.8m position it still carries **~3 m/s lateral velocity** (GT) and flies THROUGH the target -> 1.4 -> 3 -> 7m -> fly-away. Position converged, **velocity did not**.
3. **Why velocity isn't arrested: the lateral flow `h_y` UNDER-REPORTS it** — at v_lat=3.07 m/s measured `h_y`≈-0.63 (~2x under), at 11.7 m/s `h_y`≈-1.05 (~10x under). The inner loop tracks `h` (= velocity), so an under-reported `h` => under-braking => overshoot. **This is the SAME root as the descent** (loom `h_z` under-reports vertical velocity -> hard impact): optical flow under-reports velocity at close range (LK dynamic-range / 1-Z), so the controller can't brake -> overshoot (lateral) / impact (vertical).

## What was a SYMPTOM, not the cause (don't re-chase)
- **`cross(w_i,s)` / `w_iz` fabrication.** The overshoot tilts the drone -> `_getVirtualPts` (z_v->0) reprojects the in-FoV virtual centroid OFF-SCREEN (|s|->2) AND `_sensor_cal_hw` row-5 (w_z) cross-couples lateral flow into yaw: `w_z_cal = +1.0862·h_y - 0.7395·KF(w_x) + 1.0151·w_z_raw` -> fabricated `w_iz`≈-1.5 (raw yaw is clean ~0, GT-verified). That fed `cross(w_i,s)` -> corrupted `h_d` -> looked like the driver. **FIX APPLIED (cleanup, valid): w_z full-decouple — `_sensor_cal_hw[5] = [0,0,0,0,0,1.0151]` (only raw yaw); `w_iz` now clean ≈ GT. `PLASMC_WZ_CROSS=1` restores the old row.** BUT decoupling `w_iz` did NOT fix the fly-away (still overshoots with clean `w_iz`) -> proving `cross_ws` was a symptom, not the cause. ALSO: the old `PLASMC_VIRT_GUARD` s-clamp regressed (clamps genuine in-FoV s). So neither the w_iz fix nor an s-clamp is the lever.

## The lever (analog of the descent h_rd governor)
**Govern the lateral APPROACH velocity** so the drone doesn't arrive with 3 m/s it can't see — keep the closing velocity in the flow-observable range. That attacks the cause (under-reported velocity -> overshoot). `XI2_xy=0.8` (lateral flow-funnel contraction, up from baked 0.6) is the first lever that HELPED (IC2 n=5: mean xy **26.5->13.1**, **2/5 close** vs 1/5, 3 TL vs 4) — it tightens the velocity funnel faster, partially beating the overshoot, but reps still land HARD (vel 5-7.5) and 3/5 still fly away (mitigates, doesn't solve).
