## 1. Ring-sampling: root-caused, partially fixed (validated n=5 vs n=5), engagement-traced

- **s/h/alpha vs GT comparison methodology used repeatedly this session** (per [[diagnose-flight-data]] skill, now updated with this session's gotchas): align `tools/gt_optical_flow.py::compute_gt_flow`'s `t_g`/`V_s_g`/`V_h_g`/`alpha` against `Img_Data.npy`'s own `Time`/`s_V`/`h_V`/`alpha(t)`, sync-verified via `gt_t=gt['Time']+gt['Start Time']` vs `img['Time']` (median gap ~0, 95th pct <10-15ms every time it was checked — sync itself was never the problem).
- **Root cause of a `h_z` (loom) spike + subsequent freeze/miss cascade**: `n_flow_corners` collapses from ~10 to 4-5 as `MARKER_EXTENT_PX` crosses ~210-230px, dropping below `CROSS_MOMENT_LOOM_MIN_PTS=6` — below that floor the moment-loom override (MAD-filtered, robust) can't engage and the code falls back to the raw, unprotected pinv-solved `Tz`, which is far more sensitive to a single bad LK correspondence. This is the loom-spike mechanism. The subsequent "freeze" (s_V/h_V/alpha(t) becoming bit-identical across frames) is the SAME cascade's terminal end — point count hits the absolute floor (n=4), `Detection Status` flips to `'miss'` ~0.06s later, hold-last kicks in.
- **Fix**: flipped `CROSS_RING_SAMPLING` default `0`→`1` in `src/cross_marker_perception.py` (committed `94d648e`) — ring sampling's paired-opposite LK-failure rejection targets exactly this point-scarcity-near-marker-edge scenario.
- **Validated via matched n=5 vs n=5 IC2 A/B** (`test_data/RingSampling_n5_AB/`): `target_lost` 100%→60%, mean xy_err 3.72m→2.94m, point count in the 200-230px extent window improved (median 0.5→1.0, mean 3.22→4.82, %frames-below-floor 70.4%→62.9%). **Real, directionally-consistent improvement at n=5 — but modest, not a fix.** 60% target_lost is still a majority failure rate.
- **Engagement check (added `Ring Active Log` diagnostic, `(t, ring_active)` per `_compute_hw` call, exposed in `Img_Data.npy`, uncommitted)**: confirmed ring sampling had **fallen back to the unconstrained sampler during the actual failure window** in the case examined — it WAS engaged earlier in the same flight (same extent range, gave 12-23 points) but the coverage guard (`RING_MIN_COVERED_SECTORS`, marker must surround image center in ≥half of 8 sectors) correctly declined later, because the drone had drifted off-center by then. **This ties ring-sampling's limited effectiveness directly to the still-unsolved lateral-convergence-rate root cause** ([[project_20260813_cbf_extent_fix_followup]]) — it's not a flaw in the ring-sampling guard; the guard is working as designed, but the underlying centering problem denies it the geometry it needs.
- **Video-overlay debug tool built** (`CROSS_RING_OVERLAY_DBG=1` default-on when `IMG_RECORD=1`, draws tracked points green=ring-sampled/yellow=fallback onto the recorded frame, uncommitted) to visually confirm ring-sampled points land on the marker. **Attempted but inconclusive**: across 5 independent reps, none had a descent-phase (not pre-engage hover), video-covered-window (last ~5.7s only), ring-active=True, extent-200-230px overlap to actually inspect — ring sampling was never active in the video's recorded tail across any of the 5 reps, itself consistent with the engagement-check finding above. Deprioritized ("let us look at ring later") — would need either a longer recorded window or many more reps to catch this.
- **Alpha offset "bug" — investigated then RETRACTED.** Compared `alpha(t)` (perceived) to GT yaw across landing-sweep flights, found a persistent ~90° offset, initially proposed changing `CROSS_ALPHA_0` (currently 90.23°, derived from 5 dedicated phased-excitation calibration flights, std 0.18°, R²=0.97-0.99). **Retraction reason**: the code's own documented derivation uses a forced `slope=-1` fit (`alpha ≈ −GT_yaw`, physically justified — Jabbari Asl et al. 2014, `alpha_dot=−psi_dot`) — my comparison used the wrong sign convention. Redone properly (checking both `alpha_GT−alpha_p` and `alpha_GT+alpha_p`), neither showed a clean match — the data source (noisy landing-sweep flights, same point-starvation-corrupted frames as the loom investigation) is the likely reason, not the calibration itself. `CROSS_ALPHA_0` left unchanged.

## 2. GT-feedback SP investigation: two major self-corrections, then a genuine new bug found + ruled un-fixed

**⛔ Self-correction #1 (2026-08-15, see [[project_20260815_crossmarker_gtfb_sp_investigation]] for full detail)**: initially claimed "SP was never achieved with GT feedback even on fully-tuned ArUco" and "the terminal 1/Z problem was never solved" — **both wrong**. `project_why_sp_achieved` documents ArUco GT-feedback achieving 56-76% SP after a `Z_REG` 0.01→0.2 harness-artifact fix (not a control-law fix). Corrected directly by the user; root cause of my error was only searching the early (pre-breakthrough) rows of `parameter_record.ods`'s `PX4_NewCal_Record` table and stopping there.

**A NEW bug found: cross-marker GT-feedback IC2 hits a repeatable descent-stall at alt≈0.487m.** n=10 sweep (`test_data/GTFB_CrossMarker_IC2_n10/`): 4/6 completed reps hit `RuntimeError: descent stall: no >0.30m descent in 25s`, all stalling at the SAME altitude (0.487-0.49m) to 2-3 decimal places — not stochastic scatter, a repeatable attractor. 0/10 SP.

**Numerical-noise hypothesis — tested, WRONG, reverted.** Traced the stall to `h_z` reading exactly `0.0` or `~1e-28` (floating-point cancellation noise, not a real small velocity) during the stall, from `gt_feedback.py::_slope()`'s LS-slope collapsing when its position-value window becomes bit-near-identical. Implemented a fix (`_slope()` returns a `degenerate` flag via an independent y-RANGE floor check; `GTFeedback` holds the last non-degenerate velocity estimate across degenerate windows). **Tested — made the stall MORE frequent (9/10 vs 4/6), not less.** Dug deeper: compared the exact equilibrium state (`zeta_z`, `sigma_z`, `kappa_z`, `I_a_z`) between the noisy-h_z and held-h_z runs at the same stall altitude — **bit-for-bit identical to 3-4 decimal places**, proving the noise was never causal; the closed-loop system converges to the same fixed point regardless of the exact near-zero value fed in. **Reverted** (`git checkout -- src/gt_feedback.py`). The real mechanism is the kappa-adaptation leakage law (`κ̇=‖θ‖·N·G·|σ|−N·P·κ`) settling into a genuine mathematical attractor once growth balances leakage — the same class of "terminal wall" problem the historical ArUco campaign fought, just manifesting via the leakage-equilibrium mechanism (not a `Z_REG`-driven singularity, which is already fixed).

**⛔ Self-correction #2 (2026-08-17): "ArUco escapes this fixed point, cross-marker doesn't" — also wrong, based on n=1 overweighted.** Initial ArUco A/B (3 reps) found 1 rep escaping the identical 0.487m fixed point (~19-22s in, just before the 25s watchdog) while cross-marker mostly didn't — this was reported as a marker-type difference. **Ran 5 more ArUco GT-feedback reps to trace the escape mechanism (with a theta-logging fix, see §3) — 0/5 escaped.** Combined: **1/6 ArUco GT-feedback reps escaped this stall under CURRENT defaults** — far below the historical 56-76% SP rate, and not meaningfully different from cross-marker's rate. **Conclusion: the fixed point is genuinely marker-type-agnostic; ArUco is NOT reliably escaping it either under current defaults.** The gap vs. the historical 56-76% SP campaign is most likely a **config regression** (current `VDS_KF_Q=10` vs. the historically-helpful `VDS_KF_Q=1`, still the one identified, untested lever — or another undiscovered default drift), not a control-law limit and not a marker-type difference. **`VDS_KF_Q=1` test was queued but not yet run when the session ended** — top priority for next session.

## 3. CBF radius-cap investigation: hypothesis tested and falsified; a real mental-model correction along the way

**Hypothesis (falsified by direct test)**: that `CROSS_CBF_RADIUS_CAP_PX=100` (from [[project_20260814_cbf_radius_split_and_hardware_check]]) was suppressing a CBF-driven "escape kick" that rescues the z-axis from the fixed point, by capping `d_min_fov`'s sensitivity to real marker growth. **Tested raising the cap to 130 and 160** (n=3 each, both against the GT-feedback IC2 stall AND the IC3/IC4 fly-away regression, `test_data/RadiusCap_Sweep/`): **6/6 GT-feedback reps still stalled at BOTH cap values — zero effect on stall rate.** IC3/IC4 fly-away regression stayed safe (max 3.13m, no reintroduced 28m/14m-class outliers) at both caps. **Verdict: the radius cap is not the operative lever for the descent-stall; the hypothesis is falsified.** (Caught and fixed a bug in my own sweep script's `descent_stall` grep column during this — always re-verify a summary-table diagnostic column against a raw `grep` on the actual log before trusting it, one more instance of the general "verify, don't trust the derived summary" discipline.)

**⛔ Mental-model correction (user, 2026-08-20): "We stopped using funnel for CBF long back. Check cbf_visibility.py" — I had wrongly conflated `d_min_fov`/`rho_fov` with the actual CBF barrier.** Corrected understanding:
- The REAL hard visibility constraint (`cbf2_filter`'s Phase-1 QP) uses `p_10 = center/focal` (a FIXED, camera-geometry-derived quantity in normalized tangent units, e.g. `[0.889, 1.185]`) — Phase-1 is deliberately centroid-only, `radius`/`delta2` never enters the hard bound at all (per `cbf_visibility.py`'s own module docstring).
- `d_min_fov`/`rho_fov_curr` (what `CROSS_CBF_RADIUS_CAP_PX` actually governs, via `controller.py`'s own OVERFLOW/DRIFT_OFF classification) is a SEPARATE, legacy, PIXEL-space quantity, disconnected from the real barrier — and since `PLASMC_LFOV=0.0` by default, `rho_fov_curr` is FROZEN at the constant `rho_fov_0=[210,290]` for the entire flight; it never actually decays toward `rho_fov_inf=[80,80]` under default config (that funnel-decay was abandoned 2026-06-05, comment at `controller.py:507-511`).
- Practical consequence: raising `CROSS_CBF_RADIUS_CAP_PX` does NOT risk the "funnel shrinks below the cap near touchdown" failure mode I originally worried about, because that funnel never shrinks under defaults — confirmed empirically by the safe fly-away-regression result at cap=160. But since the cap sweep showed zero effect on the stall either way, this correction, while real and worth keeping, didn't end up mattering for the stall investigation's outcome.

## 4. `theta(t)` logging bug — found and fixed (uncommitted)

`Control_Data.npy`'s `"theta(t)"` was ALWAYS logging the legacy shared scalar `||Theta||_F`, even though `PLASMC_THETA_PER_AXIS=1` has been the DEFAULT since 2026-06-25 (baked specifically to decouple the axes — see that bake's own comment at `controller.py:359-370`: "the shared scalar theta=||Theta||_F couples the axes... Per-axis theta_i gives each axis its OWN uncertainty bound"). Under default config the REAL `theta_ctrl` feeding each axis's kappa-ODE is `sqrt(vector_i²+1)` (a 3-vector), which was **never saved anywhere** — a diagnosis built on the logged scalar was chasing a quantity the control law wasn't even using. **Fixed** (`self._theta` now stores whichever value is actually operative: the per-axis 3-vector by default, the legacy scalar only if `PLASMC_THETA_PER_AXIS=0` is explicitly set) and **verified working** (`Control_Data.npy`'s `theta(t)` now confirmed shape `(N,3)`). See [[diagnose-flight-data]] skill's new "watch for a field name that isn't proof" section, added because of this. **Not yet committed.** No escape event was caught under the corrected logging to actually trace the per-axis `theta_z` causal sequence at an escape point — that trace is still open for whenever an escape event (rare, ~1/6) gets caught.
